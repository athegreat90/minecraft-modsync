# Implementation report

This is a reviewable initial implementation, **not a verified production-quality MVP**. The local sandbox still lacks shell DNS/Docker access, but GitHub CI has now validated the JVM build, database tests and distributed migration/restore fixture. Native, production security and release gates remain open. Source is now published at https://github.com/athegreat90/minecraft-modsync following explicit user authorization. No PR, image or application release is claimed.

1. **Repository:** one local monorepo at `minecraft-modsync`, canonical `main`, implementation branch `feature/distributed-mvp`. GitHub default remains `main`; the source is published on `main`; retirement of the duplicate legacy branch is tracked in MEMORY.md. The neighboring `olp-server` is untouched. See [repository strategy](REPOSITORY_STRATEGY.md).
2. **Components:** ten modules separate domain, protocol, scanner, resolver, Modrinth integration, agent, client, optional TUI, backend and fixtures. See [architecture](ARCHITECTURE.md).
3. **Host A deployment:** build/extract the independent agent; mount actual Crafty storage read-only, configure its protected state and mapping aliases, enroll and assign logical servers, then run scans. [Instructions](docker/agent/README.md).
4. **Host B deployment:** provision protected secret files and persistent MariaDB volume, deploy the backend stack and a trusted HTTPS proxy, bootstrap administrator login. [Instructions](docker/server/README.md).
5. **Host C installation:** build a JVM distribution or obtain a future verified native release; configure HTTPS, verify control-plane UUID, login, register an instance, plan/apply/verify. No Docker or resident service is required. [Usage](README.md).
6. **Connection/authentication:** agents and clients independently initiate HTTPS to B; enrollment yields an agent credential, local account login yields device access/refresh credentials. Database stores credential hashes. Assignments fence stale agents. These flows executed in the Linux amd64 HTTPS fixture. [Protocol](DISTRIBUTED_ARCHITECTURE.md).
7. **Networks:** configured stable DNS supports LAN, internal CA, VPN DNS and public HTTPS proxy deployments. No direct A-C path, inbound agent API, client database connection or cross-host bind mount exists. [Networking](NETWORKING.md).
8. **Migration:** explicit assignment transfer for A, consistent database restore and fenced DNS cutover for B, new device registration/profile retrieval for C. [Procedures](HOST_MIGRATION.md).
9. **Backup/recovery:** checksum-verified export/import scripts use MariaDB utilities and protected option files. Script transport/escaping tests passed against fakes; a real MariaDB restoration drill passed in the isolated GitHub CI fixture. [Database guide](DATABASE.md).
10. **Performance:** no native, resident-agent, memory, CPU, throughput or synchronization measurements exist. A benchmark harness reports process startup/file size and explicitly leaves other fields unmeasured. [Evidence policy](CLIENT_PERFORMANCE.md).
11. **Release behavior:** workflow definitions reconcile reachable main commits, build exact revisions, validate platforms/security and finalize deterministic prereleases only after success. They require explicit repository configuration and have not run. [Release guide](RELEASES.md).
12. **Images/artifacts:** Dockerfiles target independently packaged server/agent multi-architecture images; workflows define three native client platforms and agent/JVM artifacts. No built or published digest/binary is claimed.
13. **Executed checks:** seven Python tests passed (four release reconciliation, three fake backup transport); module/deployment boundary checks, Python compilation, shell syntax, Markdown local links and both production Compose configuration checks passed. The Java health probe compiled for Java 25. Local Gradle/Docker execution remained blocked; GitHub CI subsequently passed 26 Kotlin/MariaDB tests, 11 Python tests and the full distributed fixture. The final source scan flagged its temporary TLS key; scan order is corrected in the follow-up.
14. **Security:** implemented TLS verification, identity checks, Argon2id, revocation/rotation, role authorization, assignment generations, request/rate limits, audit correlation, read-only mounts, safe filenames, official-CDN constraints and SHA-512/CRC verification. Baseline authorization, TLS, integrity and ownership behavior executed in the fixture; comprehensive production security review remains open. [Threat model](SECURITY.md).
15. **Limitations:** no official wrapper JAR, resolved dependency verification/locks, live OpenAPI contract verification, measured native workflows, complete Windows ACL handling, Crafty API adapter, persistent hash/catalog cache or retention policy. Missing dependency pins block rather than guess. See [MEMORY.md](MEMORY.md).
16. **Next work:** retain the passing JVM/MariaDB/TLS/restoration checks and finish native/platform/production-security validation; collect representative benchmarks; pin verified supply-chain artifacts; then configure branch protections/registry and prepare validated follow-up PRs/releases. The [MVP checklist](docs/deployment/MVP_CHECKLIST.md) intentionally remains unchecked pending evidence.
