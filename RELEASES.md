# Releases

`main` is the canonical release branch. Source is published at https://github.com/athegreat90/minecraft-modsync. GitHub default and canonical release branch are both `main`. Development prereleases publish automatically after the required validation, native-platform and security gates. No repository-variable opt-in is required. Stable releases and deployments remain separate actions. A release is complete only after its visible assets and image digests are verified.

The reconciler runs after the `validate` workflow of a main push has succeeded (that workflow includes the SonarQube quality gate, so a failed analysis blocks the release), hourly and manually; hourly and manual runs first require a successful `validate` run for the tip of `main`. It walks every reachable commit, excluding published releases and active jobs, and dispatches a bounded batch. Multi-commit pushes and merges are therefore covered. The latest eligible main commit is selected first; historical unattempted commits then take priority over historical retries. Canceled attempts retry six hours after their last update; failed or timed-out attempts back off exponentially (6h, 12h, 24h, ... capped at 7 days, doubling per failed attempt) so a commit that cannot build is not rebuilt every six hours. Commits whose `.github/workflows` differ from the tip of `main` are never dispatched and are listed as `unpublishable` in the reconciliation log: the workflow token cannot create the temporary branch or the tag for them (HTTP 403), so their publication would only fail. In practice only the latest commit and commits merged without touching the workflows are released. Only commits from `RELEASE_FLOOR` (`7c29453`) onwards are reconciled: the previous floor `d9f75f5` can never pass native dependency verification, because the `graalvm-reachability-metadata` checksum was added by the next commit. Canceled pending reconciliation/release jobs are recovered by subsequent passes. Run history and failed Actions jobs report failures; no failed validation becomes a successful prerelease.

Each build first proves in a cheap `version` job that the SHA is a reachable `main` commit and derives the version and the Gradle version pinned by that source (`gradle/wrapper/gradle-wrapper.properties`, so a historical commit is built with the Gradle its dependency checksums were generated for, not with the one `main` uses today); then `validate` (tests, boundaries, source security scan, JVM distributions), `integration` (the TLS distributed fixture) and the native builds on Windows x64/Linux x64/Linux ARM64 run in parallel, each on a checkout of that exact SHA. `publish` needs all of them, so nothing is published unless every gate passed. Image publication builds amd64/arm64 images with provenance and SBOM attestations (the Gradle build stage of both Dockerfiles is pinned to `--platform=$BUILDPLATFORM`, so the platform-independent JVM artifact is compiled once natively instead of once per target under QEMU, which had taken about 50 of the 72 minutes of a release), scans immutable digests (Trivy is pinned to v0.76.2 for the source scan in `ci.yaml`/`release.yaml` and for the image scan in `publish.py`; `trivy-action` stays at its latest release, v0.36.0, pinned by commit SHA) and only then finalizes a prerelease.

Versions are deterministic `v<version>-dev.<commit-UTC-timestamp>.<full-sha>`, where `<version>` is the application version of the built source (a historical commit keeps its own, for example `v0.3.2-dev...`; the current one is `v0.6.5-dev...`). Publication checks that the `<timestamp>.<full-sha>` part matches the checked-out commit and that the whole tag is well formed, and never compares the `<version>` prefix, because publication runs the current tooling against historical sources. Immutable lightweight source tags identify the exact commit. Publication checks repository write permission and actual GHCR push authorization before creating a tag/draft. Draft publication can be retried only after validating the target and tag against the exact source. Required assets are downloaded and checked against the compatibility manifest/checksum index, and both image digests must resolve before finalization. Finalized releases are verified without mutation; reconciliation reports incomplete or mismatched releases as errors. Current publication tooling is retained when building historical sources. GHCR tags are technically mutable by registry administrators: protect credentials and deploy by recorded digest. Registry-enforced tag immutability and GitHub immutable-release settings require operator configuration.

Assets include native CLI/agent builds, JVM ZIPs, server JAR, benchmark JSON, checksums and `release-manifest.json`. Images use `ghcr.io/<owner>/minecraft-modsync-{server,agent}:<version>`. The compatibility manifest records source, API/agent protocols, minimum versions, image digests, checksums and schema/migration notes. Stable promotion and production deployment are deliberately separate, explicit procedures.

JVM/database/source-security/distributed checks have passed in prior main CI. Native builds and the first visible prerelease remain unverified for this change. Remaining limitations: action SHA pinning, official Gradle wrapper generation, resolved dependency locks/verification metadata, signed checksums and representative resource benchmarks remain gates. Native smoke tests currently exercise command startup; full native synchronization still needs coverage. Intermediate historical commits lacking the complete system can fail validation and remain visibly failed rather than being relabeled successful.

**Retention: one release per version.** Only the newest build of each application version is kept. The reconciler treats a commit as superseded (neither built nor counted as remaining) when a later commit of the same version already has a verified release, reading each unreleased commit's version from its own `scripts/release/reconcile.py`; commits whose version cannot be read are never skipped. To remove the older duplicates run `python3 scripts/release/prune.py` from `scripts/release` with `GITHUB_REPOSITORY=<owner>/<repo>` and an authenticated `gh` (it is a dry run), then add `--apply` to delete them with their tags. It only considers published, non-draft development releases, never touches drafts, and does nothing for a version whose newest release fails `verify_complete`, so the last good release of a version cannot be deleted. Deleting needs permission to delete tags (tag protection can block the workflow token, so run it with your own credentials). GHCR image tags (`ghcr.io/<owner>/minecraft-modsync-{server,agent}:<version>`) are not removed by this tool; delete the old package versions in the GitHub package settings or with `gh api -X DELETE` and a token with `delete:packages`. Merge the reconciler change before pruning, otherwise the hourly reconcile would rebuild the deleted releases. Draft releases (leftovers of failed publish attempts, usually with no assets) are never deleted by the tool; list them with `gh release list` and remove each with `gh release delete <tag> --cleanup-tag --yes` once you are sure they are abandoned.

See [deployment release operations](docs/deployment/README.md#automatic-development-prereleases) for reconciliation and publication details.

## Main branch protection and legacy cleanup

After merging the main-branch migration PR, run `python3 scripts/repository/apply_main_policy.py` from a network-capable checkout authenticated with `gh` and repository administration permission. This makes main default, adds baseline protection if none exists, verifies it, then retires master only when it has no unique commits and differences are limited to the reviewed migration files. The baseline requires a PR, one approving review, the up-to-date `validate` check and resolved conversations; it applies to admins and prohibits force pushes/deletion. Existing protection policies are retained rather than overwritten. If no second reviewer is available, an administrator must deliberately choose an appropriate review policy; this script does not silently relax it.

Repository settings have not been changed by the current sandbox: the connector lacks administration/delete-ref actions and terminal GitHub access is unavailable. The helper has unit coverage but no successful live administration execution.

## Quality gates in validation

Both the per-commit validation and the release validation run `check` (tests, Detekt, Spotless) and `dokkaGenerate`. Spotless checks only changed files; the release job passes `-Pspotless.ratchetFrom=HEAD` because its checkout has no `origin/main` ref. The SonarQube job (`ci.yaml`) runs on a GitHub-hosted runner that joins the tailnet through the Tailscale GitHub Action (see `docs/development/SONARQUBE.md`) and never runs for pull requests.
