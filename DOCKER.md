# Docker deployment

Use `docker/server/compose.yaml` on Host B and `docker/agent/compose.yaml` on Host A. Their networks are local to each Docker host. Never connect production hosts using cross-host bind mounts or a shared Docker socket.

Images use JRE 25, an explicit non-root application UID/GID 10001 and versioned base tags. Server/agent images support intended amd64/arm64 builds through Buildx; actual execution remains unverified. Digest pinning must follow successful image builds/security review.

Host B has a persistent database volume and no database published port. Its app filesystem is read-only with a bounded temporary directory. The loopback API binding requires a separately configured trusted TLS proxy. Database secrets and bootstrap credentials are mounted files.

Host A mounts the actual host Crafty storage read-only and a separate writable agent-state directory. For Crafty's `/crafty/servers`, locate the host bind mount configured in Crafty's existing deployment, then mount that host path into the agent as `/minecraft`. The agent has no authority to modify Crafty, restart Minecraft, or edit worlds.

Configure the state directory ownership for UID 10001 before running. Grant the agent only read/search access to intended server directories. `modsync-agent map alias /minecraft/server/mods` records the agent's own visible path. Backend assignments refer to `alias`, never to another container's filesystem.

A conventional dev include exists at `docker/dev/compose.yaml`; the meaningful distributed fixture is generated by `scripts/integration/distributed.py`. It separates A-B/C-B networks, supplies synthetic mods/API/CDN and an isolated restore target. It requires no Minecraft account or live Crafty instance.

Troubleshoot DNS and HTTPS from each host independently, then identity/authentication, mapping permissions and database readiness. Never solve a permission failure by mounting the Docker socket or making all Minecraft files writable.
